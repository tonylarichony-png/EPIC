# ISSUE-001 — EXP-009: kernel crash при подсчёте CpG

← [[issues/_index.md|Реестр проблем]] · [[experiments/EXP-009.md|EXP-009]] · [[README.md|Dashboard]]

## Кратко

- **Что произошло:** kernel Jupyter завершался на построении `train_cpg_counts` без Python traceback.
- **Влияние:** EXP-009 нельзя было довести даже до CV; обучение модели ещё не начиналось.
- **Причина:** непрерывный `CpG O/E201` создавал почти отдельную агрегированную строку для каждой позиции, а реализация дополнительно держала в памяти несколько полноразмерных массивов и результаты всех батчей.
- **Тип отказа:** исчерпание оперативной памяти (OOM) и завершение процесса Python операционной системой.
- **Потеря данных:** нет; immutable run эксперимента ещё не был создан.

## Ожидаемое и фактическое поведение

- **Ожидалось:** точно свернуть train по одинаковым признакам и получить компактную таблицу достаточных статистик для логистической регрессии.
- **Получили:** процесс Python исчезал во время `split_kmer_cpg_counts(...)`, поэтому Jupyter показывал перезапуск kernel вместо обычного исключения.
- **Почему restart не помогал:** после перезапуска выполнялся тот же детерминированный расчёт с тем же пиком памяти; причина не находилась в испорченном состоянии kernel.

## Контекст и воспроизведение

- **Эксперимент:** [[experiments/EXP-009.md|EXP-009 — EXP-007 + CpG O/E201]].
- **Notebook:** [[notebooks/experiments/EXP-009_cpg_oe201_logistic.ipynb]].
- **Падавший шаг:** полный подсчёт train в вызове `split_kmer_cpg_counts(...)`.
- **Важно:** падение происходило до `cross_validate_cpg_logistic(...)`; solver и параметры логистической регрессии здесь ни при чём.

## Что именно съело память

Изначально признак использовался как непрерывное число:

```text
CpG O/E201 = CpG_count × valid_ACGT / (C_count × G_count)
```

Для точного сворачивания две позиции можно объединить только тогда, когда у них
совпадают **все** признаки. У позиций с одинаковыми `6-mer` и `GC-bin` часто
различаются `C_count`, `G_count` или `CpG_count`, а значит различается и raw
`CpG O/E201`. Поэтому число групп приблизилось к числу исходных позиций.

Дополнительно первая реализация одновременно создавала:

1. uppercase-копию всей последовательности contig;
2. массивы для кодирования k-mer и неизвестных оснований;
3. четыре полноразмерных prefix-массива для `C`, `G`, `ACGT` и `CpG`;
4. списки уникальных строк каждого батча;
5. общий `concatenate` и сортировку всех накопленных результатов.

Пиковое потребление памяти было значительно больше размера итогового DataFrame.
Когда память закончилась, ОС завершила Python-процесс. Поэтому traceback не
появился: обработчику исключений Python уже было нечего показывать.

## Диагностические измерения

| Проверка | Позиции | Уникальные строки | Размер итоговой таблицы |
|---|---:|---:|---:|
| Continuous CpG, первые 2 млн позиций | 2 000 000 | 1 163 313 | 22.19 MiB |
| Continuous CpG, один strand `NC_064035.1` | 16 728 378 | 12 939 204 | 246.8 MiB |

Уже на одном strand сохранилось около 77% исходных позиций. На полном train это
означало бы многогигабайтную таблицу плюс временные массивы и копии при merge и
sort. Следовательно, проблема была не случайной и масштабировалась вместе с
датасетом.

## Root cause

Root cause состоял из двух частей:

1. **Высокая кардинальность признака.** Continuous `CpG O/E201` почти не давал
   сворачивать наблюдения, хотя весь план exact-обучения опирался на компактные
   повторяющиеся категории.
2. **Неограниченный пик памяти.** Полноразмерные prefix-массивы и финальное
   объединение всех batch-результатов одновременно удерживали слишком много
   данных.

Это не просто медленный алгоритм. Исходное представление признака было
непригодно для выбранной схемы точного обучения на полном train.

## Решение

- Raw-формула сохранена, но её значение переводится в заранее заданные bins:
  `<0.25`, `[0.25,0.50)`, `[0.50,0.75)`, `[0.75,1.00)`, `[1.00,1.25)`,
  `[1.25,1.50)`, `>=1.50`, `missing C/G`.
- Reference-bin — `[0.75,1.00)`; модель получает семь contrast-признаков.
- Агрегация теперь выполняется точно по
  `contig × strand × 6-mer × GC-bin × CpG-bin`.
- Последовательность обрабатывается ограниченными чанками по 250 000 позиций с
  необходимым halo вокруг окна.
- Промежуточные группы объединяются иерархически, без накопления всех batch-таблиц
  перед одним огромным `concatenate`.
- Для положительных позиций статистики окна считаются разреженно.
- Добавлен прогресс по каждому `contig × strand`, чтобы долгий подсчёт не выглядел
  как зависание.

## Что означает «точно» после исправления

Точная likelihood сохранена **для новой binned-модели**: каждая строка таблицы
представляет все позиции с полностью одинаковыми признаками, а multiplicity
передаётся через `sample_weight`. Sampling не используется.

При этом binned-модель не математически тождественна первоначальной модели с
непрерывным ratio. Это осознанное изменение представления признака ради
ограниченной кардинальности, и оно зафиксировано в протоколе EXP-009 до обучения.

## Проверка исправления

| Проверка | Результат |

| Полный `NC_064035.1`, оба strand | 33 456 756 позиций |
| Итоговая binned-таблица | 417 449 строк |
| Размер итоговой таблицы | 6.37 MiB |
| Время диагностического прогона | 13.27 s |
| Автоматические проверки реализации и notebook | 51 passed, 48 subtests passed |

Полное обучение EXP-009 намеренно не запускалось: notebook остаётся под ручным
контролем.

## Защита от повторения

Перед добавлением любого признака, по которому планируется exact-агрегация:

- [ ] Посчитать теоретическую максимальную кардинальность категорий.
- [ ] Сделать pilot на 1–2 млн позиций и измерить долю `unique rows / positions`.
- [ ] Сделать pilot на одном самом длинном `contig × strand`.
- [ ] Оценить не только размер результата, но и временные копии при concat, sort и merge.
- [ ] Обрабатывать длинные последовательности bounded chunks с halo, а не набором полноразмерных prefix-массивов.
- [ ] Не хранить результаты всех батчей до одного глобального объединения.
- [ ] Выводить прогресс и размер агрегата по `contig × strand`.
- [ ] Явно писать, относительно какого преобразования признака loss остаётся точной.
- [ ] Если kernel исчез без traceback, сначала проверять OOM или native crash, а не параметры solver.
