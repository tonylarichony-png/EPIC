# Единый процесс экспериментов EPIC

## Главная идея

Для каждого нового эксперимента создаётся **отдельный notebook**, но общая
подготовка данных не копируется. У нас три разных уровня ответственности:

```text
raw-файлы
    ↓
src/ml_project/epic_data.py          одно правило данных для всех экспериментов
    ↓
фиксированный contig_holdout_v1      один и тот же train/validation/test
    ↓
notebooks/experiments/EXP-xxx.ipynb  одна гипотеза, признаки, модель, метрики
    ↓
карточка + artifacts/                объяснение решения и точная запись запуска
```

Это позволяет читать эксперимент сверху вниз и при этом не искать отличия в
десятках скопированных функций подготовки.

## Что вынесено в общий Python-модуль

Источник истины — `src/ml_project/epic_data.py`. Он отвечает за:

- поиск файлов `jaNemVect1.1` и проверку их наличия;
- чтение FAI, whitelist и template;
- проверку BED-координат, порядка интервалов и двух цепей;
- объединение `csRNA-r1 + csRNA-r2`;
- построение бинарного target `count > 0`;
- фиксированное разбиение **целых contig**;
- сохранение manifest и SHA-256 исходных/производных файлов;
- восстановление всех нулевых позиций потоковыми batch без таблицы на сотни
  миллионов строк.

Sampling, ДНК-признаки, архитектура модели и метрики сюда намеренно не входят:
это изменяемая и поэтому видимая часть конкретного эксперимента.

В notebook эксперимента общий слой подключается одинаково:

```python
from ml_project.epic_data import ensure_prepared_split

split = ensure_prepared_split(PROJECT_ROOT)
```

## Что берём из Titanic-проекта

Из `D:/Projects/Titanik-ML-project/notebooks` полезен не конкретный CSV-код, а
организация исследования:

- эксперимент имеет стабильный `EXP-ID`;
- гипотеза, одно основное изменение и критерий успеха записываются **до** fit;
- общий код находится в `src/`, а notebook остаётся читаемым сценарием;
- параметры, метрики, версии данных и решение сохраняются;
- неудачные эксперименты не удаляются.

Для EPIC сделана важная адаптация: notebook каждого эксперимента является
отдельным отслеживаемым документом в `notebooks/experiments/`. Табличный
Titanic-workbench нельзя переносить буквально, потому что здесь сотни миллионов
position-strand, BED/FASTA, sparse target и группировка по contig.

## Сравнение с `epic_solution/code`

| Аспект | `epic_solution` | Текущий EPIC-процесс |
|---|---|---|
| Базовая единица | position-strand из template | та же |
| Повторности | pooled `r1 + r2` | то же |
| Разделение | целые contig | то же |
| Хранение target | разреженные ненулевые значения | то же |
| Последовательность | заранее кодируется в `seq.u8`, читается через memmap | будет отдельным общим feature-слоем, когда понадобится модели |
| Holdout | target-aware подбор `tune` и `report` примерно по длине и доле positives | target-blind permutation с seed 42: 9 train, 3 validation; официальный test отдельно |
| Назначение кода | быстрый end-to-end CNN pipeline | обучение, интерпретируемость и сравнимый журнал гипотез |
| Test в подборе | demo sweep вызывает оценку на `sub=test`, поэтому demo-test участвует в диагностике архитектур | test labels не читаются; выбор делается только по validation |
| Запись эксперимента | shell-команды и выходные файлы | отдельный notebook, Markdown-карточка и JSON/CSV record |

Иными словами, низкоуровневые идеи подготовки совпадают. Отличаются политика
оценки и назначение: внешнее решение оптимизировано под обучение CNN, наше — под
понятное и честное исследование. Если позже понадобится скорость внешнего
решения, можно добавить совместимый `seq.u8`/memmap слой, не меняя split.

## Как начать новый эксперимент

В Miniforge Prompt из корня проекта:

```bat
conda activate epic-eda
cd /d D:\Projects\EPIC\EPIC
new-epic-experiment.cmd
```

Команда сама найдёт последний принятый эксперимент с сохранённым immutable run
(сейчас это `EXP-009/run_001`), затем спросит название, гипотезу, единственное
изменение, критерий успеха и место реализации. По умолчанию создаются три файла:

- `notebooks/experiments/EXP-xxx_<slug>.ipynb` — исполняемый эксперимент;
- `experiments/EXP-xxx.md` — короткая карточка решения.
- `src/ml_project/epic_experiments/exp_xxx_<slug>.py` — только код нового
  признака, bounded-memory подсчёта и candidate-модели.

Все ячейки остаются невыполненными. В notebook заранее стоят отдельные флаги и
STOP-точки перед feature pilot, полным train count, CV, full fit и validation.
Генератор не запускает вычисления и не создаёт `run_001`. Если небольшое
нововведение удобнее оставить в notebook, выберите режим `notebook`.

Можно передать всё без диалога:

```bat
new-epic-experiment.cmd ^
  --title "Контекст 101 bp" ^
  --hypothesis "Широкий контекст улучшит AP" ^
  --change "Только ширина окна" ^
  --success "Validation AP выше reference минимум на 0.01" ^
  --implementation module ^
  --yes
```

`--parent EXP-009` явно фиксирует champion, `--experiment-id EXP-010` — номер,
а `--implementation notebook` оставляет заготовки функций в отдельной ячейке.

## Обязательная структура experiment-notebook

1. **Протокол до запуска:** гипотеза, одно изменение, критерий успеха.
2. **Data contract:** загрузка фиксированного split и показ его версии.
3. **Параметры:** все числа и режимы в одном словаре.
4. **Реализация:** одинаковые позиции для reference и candidate.
5. **Результаты:** отдельно Average Precision и EPIC Spearman для reference и
   candidate, затем разбивка по contig.
6. **Интерпретация:** почему получился результат и где ограничения.
7. **Решение:** `adopt`, `reject`, `iterate` или `inconclusive`.
8. **Запись:** JSON/CSV в `artifacts/experiments/<EXP-ID>/<run_name>/`.

## Правила сравнимости

- Не менять `contig_holdout_v1` между сопоставимыми экспериментами.
- Не подбирать параметры по официальному test.
- Для reference и candidate использовать одинаковый sampling и считать обе
  обязательные метрики.
- Менять одну главную причину за эксперимент.
- Не перезаписывать `run_001`: новый запуск получает новое имя.
- Если изменились target, split или основная метрика, начать новую линию
  сравнения и явно записать это в карточке.
