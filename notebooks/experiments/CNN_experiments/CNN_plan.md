# CNN для EPIC: гипотезы и план на одном ПК

[[notebooks/experiments/CNN_experiments/CNN_baseline.ipynb|Рабочий notebook]] · [[docs/00_problem.md|Задача]] · [[docs/03_validation.md|Валидация]]

## Цель и договорённости

Исследуем связь ДНК с положением и интенсивностью начала транскрипции у Nematostella. Ответ — csRNA-сигнал для каждой оцениваемой позиции и цепи; обязательные метрики — Average Precision и EPIC Spearman.

Начинаем с собственной компактной CNN, обучаемой со случайных весов на данных проекта. Пользователь сам заполняет notebook; помощь в чате идёт небольшими шагами, с объяснениями по запросу. Учебные датасеты вместо EPIC не используем.

**Этот документ — план и набор проверяемых гипотез, а не результаты экспериментов.** Параметры ниже, обозначенные как предложения, ещё не выбраны измерениями. Новые EXP-ID этой заметкой не регистрируются.

## Можно ли работать на нашем ПК?

**Да: компактные CNN, их обучение с нуля и содержательные сравнения — реалистичное направление для этого ПК.** Улучшение качества относительно существующих моделей нужно доказать экспериментом; высокое место в конкурсе заранее не обещаем.

| Ресурс | Что известно |
|---|---|
| GPU | AMD Radeon RX 6750 GRE, 12 GB видеопамяти; название подтверждено пользовательским тестом DirectML |
| RAM | Около 32 GiB по документации проекта; текущее свободное количество не измерено |
| Среда | Windows, Miniforge `epic-eda`, Python 3.12 |
| Пакеты | `torch==2.4.1`, `torchvision==0.19.1`, `torch-directml==0.2.5.dev240914`, по выводу пользователя |
| Выполненная проверка | Тестовая Conv2d: forward, loss и backward завершились, тензоры и градиенты — `privateuseone:0` |
| Ещё не проверено | Полная 1D CNN, выбранный loss, optimizer step, скорость обучения, пиковая память и полный inference |

Уточнение к прежнему обсуждению: наличие `privateuseone:0` у входа и выхода само по себе **не доказывает отсутствие промежуточного CPU fallback**. DirectML допускает выполнение неподдерживаемых операторов на CPU; это отражено в [описании Microsoft на PyPI](https://pypi.org/project/torch-directml/). Проверяем конкретный обучающий путь, предупреждения и фактическую GPU-активность. Отсутствие предупреждений тоже не заменяет профилирование, если остаются сомнения.

Обучающие вычисления хотим выполнять на GPU. Чтение FASTA, формирование батчей и подсчёт метрик на CPU допустимы. Если модель упирается в несовместимую операцию, сначала ищем поддерживаемую реализацию; незаметно переводить обучение на CPU не будем.

## Представление данных и направление модели

- Вход: one-hot A/C/G/T/N-or-edge, форма `[batch, 5, L]`. Нижний регистр пока объединяем с верхним, как в существующем извлечении контекста.
- Пятый канал объединяет неизвестную букву и выход за границу контига — это упрощение baseline, а не утверждение об их биологической эквивалентности.
- Рабочее предложение для выхода: профиль центрального участка, `[batch, 2, P]`, с каналами `+` и `-` и разрешением один нуклеотид. Размер `P` и окончательная функция потерь ещё не выбраны.
- Для двухцепочечного выхода удобно держать вход в прямой геномной ориентации. При reverse complement нужно одновременно разворачивать профиль и менять каналы цепей местами. Это отличается от текущих признаков, ориентированных отдельно по цепи.
- Нужна отдельная маска размеченных выходных позиций. Пятый входной канал не заменяет её. Вне размеченного домена неизвестный target нельзя считать нулём.

Предлагаемое ядро: полностью свёрточная 1D-сеть с небольшим числом каналов; при расширении контекста — residual-связи и dilated-свёртки. Ориентир для первого проекта архитектуры: 32–64 канала и несколько блоков, желательно существенно меньше миллиона параметров. Это предложение, не гарантия расхода памяти: существенны длина входа, активации, batch и рабочие буферы.

В основной профильной ветви сначала сохраняем разрешение по нуклеотидам. Ранее предложенные `MaxPool → Flatten → Linear` не считаем принятой архитектурой для профильного выхода.

## Гипотезы

Обозначения `CNN-H*` действуют только внутри этого плана.

| Гипотеза | Проверка | Когда идея заслуживает продолжения |
|---|---|---|
| CNN-H1. Локальные обучаемые мотивы полезны сверх наших ручных признаков | Компактная CNN против зафиксированного reference на одинаковых оцениваемых позициях | Улучшение заранее выбранной метрики при допустимом изменении второй |
| CNN-H2. Более широкий контекст добавляет информацию | Несколько заранее выбранных масштабов при одинаковом выходном участке и контроле доступного модели контекста | Прирост воспроизводится и оправдывает дополнительное время/память |
| CNN-H3. Профильный выход позволяет экономнее сканировать геном | Измерить число предсказанных position-strand в секунду, обработку перекрытий и качество | Полный проход укладывается в наш бюджет без ухудшения оценки |
| CNN-H4. Разделение формы профиля и общей интенсивности улучшает результат | После простого baseline сравнить прямое предсказание сигнала с двумя головами по идее ProCapNet | Выигрыш по AP/Spearman сверх простой постановки |
| CNN-H5. Совместное использование точного локального и широкого контекста полезно | Компактная многомасштабная CNN после проверки CNN-H2 | Прирост нельзя объяснить только увеличением числа параметров |
| CNN-H6. Attention или Hyena дают пользу сверх сравнимой CNN | Только отдельный поздний эксперимент после подтверждения потребности в дальнем контексте | Качество и стоимость лучше доступного CNN-reference |

Для CNN-H4 полностью нулевые окна требуют особого обращения: у них нет наблюдаемого распределения положительного сигнала по позициям, но они должны обучать предсказание низкой интенсивности. Две головы и баланс их losses — отдельная гипотеза, не обязательная сложность первой модели.

## Как искать окно контекста

Польза GC201 в прежних экспериментах **не доказывает оптимальность окна 201 для CNN**.

Предварительные ориентиры для поиска — масштабы около 201, 401, 801 и 1601 нуклеотида вокруг отдельной предсказываемой позиции. Не запускаем сразу полную сетку; после пилота достаточно сравнить короткий и более широкий контекст, затем уточнить перспективный диапазон.

Различаем три величины:

- `L` — длина входной ДНК;
- `P` — длина центрального выходного участка;
- receptive field — какие входные позиции действительно способны повлиять на один прогноз.

При выходном участке длины `P` и контексте по `r` оснований с каждой стороны вход имеет длину `L = P + 2r`. Для честного сравнения фиксируем `P` и оцениваем одни и те же геномные позиции. Проверяем, что архитектура действительно использует добавленные фланги: удлинение входа сверх receptive field само по себе контекст не расширяет.

Если для большего receptive field меняем глубину, dilation или ширину сети, записываем это явно: такой эксперимент меняет не только окно. По возможности делаем контроль доступного контекста при одинаковой архитектуре, например одинаково маскируя дальние фланги при обучении и оценке каждого варианта.

## План движения

1. **Зафиксировать контракт одного примера.** Вход, ориентация цепей, выходной участок, pooled counts, маска и преобразование target. Использовать существующие split и адресацию; проверить несколько настоящих окон вручную.
2. **Проверить маленькую CNN на GPU.** Forward → выбранный loss → backward → optimizer step. Проверить конечность чисел, изменение весов и способность подогнаться к маленькому фиксированному набору. Это техническая проверка, не оценка обобщения.
3. **Измерить стоимость.** После прогрева измерить полный шаг обучения и блочный inference с ожиданием завершения GPU-операций; записать память, скорость и время загрузки данных. Оценить продолжительность более крупного запуска.
4. **Получить первый ограниченный baseline.** Одна конфигурация, фиксированные seed, train-sampling и диагностическая выборка. Сохранить checkpoint, кривые и обе метрики. До запуска установить лимит времени/шагов и критерий остановки.
5. **Проверить контекст.** Один изменяемый фактор за эксперимент; сначала два масштаба. Фиксировать число увиденных примеров, шагов, effective batch и время, чтобы не спутать контекст с объёмом обучения.
6. **Подтвердить shortlist.** Лучшие один-два варианта проверить повторными seed и на полном validation whitelist; сопоставить с действующим принятым reference. Быстрый screening не объявляет нового champion.
7. **Усложнять по результатам.** Сначала профиль/intensity heads или многомасштабная CNN; attention/Hyena и сочетания — после измеримого основания. После фиксации модели — воспроизводимый сканер и подготовка конкурсного выхода.

## Как удержать расходы в рамках одного ПК

Предлагаемые стартовые ограничения, которые уточняем после пилота:

| Этап/ресурс | Практический предел |
|---|---|
| Smoke-test | Примерно 5–10 минут, десятки полных шагов |
| Первичный screening | Один запуск одновременно, ориентир 20–30 минут на конфигурацию |
| Подтверждающий запуск | Сначала лимит 2–4 часа; увеличивать осознанно по результатам и оценке скорости |
| GPU batch | Начать с малого, например 4–8 окон, затем увеличивать по измерениям |
| VRAM | Оставлять запас для Windows и рабочих буферов; ориентир занятой выделенной памяти до 8–9 GiB, а не все 12 GB |
| RAM | При подтверждённых 32 GiB ориентироваться на общий расход процесса до 20 GiB, включая оценку метрик |
| Численная точность | Начать с FP32; поддержку и пользу mixed precision на DirectML не предполагать |

Это **лимиты расходов**, а не обещание сходимости или окончания обучения за указанное время. Одного короткого неудачного запуска недостаточно, чтобы признать архитектуру бесполезной.

Геном храним компактно, one-hot создаём только для текущих батчей. Не материализуем все перекрывающиеся окна. Если малый batch мешает эксперименту, отдельно проверяем накопление градиентов с корректным масштабированием loss; оно не устраняет память активаций одного microbatch.

Для обучения допустима зафиксированная смесь окон с сигналом и фоновых окон из train. Не обучаемся только на пиках. Обогащение положительными меняет распределение: сохраняем схему и вероятности отбора, отдельно решаем вопрос весов и калибровки. При сравнении архитектур схему не меняем.

Для inference используем непрерывные блоки с флангами и выдаём только центральный участок. Правило перекрытий фиксируем; каждую оцениваемую позицию учитываем один раз либо заранее определённым агрегированием.

## Честная оценка при больших данных

Основа — существующий `contig_holdout_v1`, без случайного разделения перекрывающихся окон. По [[docs/03_validation.md|текущему протоколу]] локальный train содержит 228 064 160 position-strand, validation — 83 807 486. Поэтому полный проход и метрики могут стоить больше одного короткого обучения.

- Для быстрых проверок заранее фиксируем небольшую диагностическую выборку с естественным фоном и достаточным числом положительных позиций. Это оценка на подвыборке, не полная validation AP; reference оцениваем на тех же строках.
- Финальные AP и EPIC Spearman считаем по исходному протоколу. AP на искусственно сбалансированной выборке нельзя сравнивать с AP полного whitelist.
- EPIC Spearman: корреляция Pearson между **dense ranks** target и score только на `target > 0`; обычный `spearmanr` не является точной заменой.
- Один и тот же итоговый score используем для обеих метрик. Если есть несколько голов, способ их объединения фиксируем заранее.
- AP нельзя получать усреднением AP отдельных батчей. Планируем память/диск для глобального ранжирования, например через дисковое хранение и сортировку; точную реализацию ещё предстоит выбрать. Приближённую метрику явно маркируем и не выдаём за точную.
- Критерий принятия заранее задаёт желаемый прирост одной метрики и допустимое изменение второй. Вместе с качеством показываем стоимость. Test не используем для выбора архитектуры/окна; история ранее выполненных проверок отражается в отчёте.

## Какие идеи берём из обсуждённых моделей

| Семейство | Место в нашем плане |
|---|---|
| [ProCapNet/BPNet](https://github.com/kundajelab/ProCapNet) | Главный ориентир для профильной CNN и гипотезы «форма + количество». Исходный PRO-cap и наш csRNA-seq различаются; копировать результаты и протокол без проверки нельзя. |
| [SpliceAI](https://www.illumina.com/science/genomics-research/articles/predict-splicing-primary-sequence-deep-learning.html) | Идеи residual/dilated-свёрток для контекста. Исходная задача — сплайсинг. |
| [Borzoi](https://www.nature.com/articles/s41588-024-02053-6) | Идеи сочетания локальных признаков, дальнего контекста и U-Net. Оригинальные ~524 kb входа и 32 bp выхода не принимаем как наши параметры; нужен выход с разрешением 1 bp. |
| [SegmentNT](https://www.nature.com/articles/s41592-025-02881-2) | Идея многомасштабного выхода на каждый нуклеотид. Опубликованная модель использует pretrained NT и предсказывает классы геномных элементов. |
| [DNABERT-2](https://github.com/MAGICS-LAB/DNABERT_2) | Возможное позднее сравнение с attention. Собственная модель с нуля не наследует качество предобученного encoder. |
| [HyenaDNA](https://github.com/HazyResearch/hyena-dna) | Возможная альтернатива для длинного контекста, допускающая обучение с нуля. Польза для нашей задачи и совместимость конкретной реализации с DirectML ещё не проверены. |

Полное воспроизведение больших опубликованных моделей и масштабное предобучение не входят в стартовый бюджет. Облачные GPU и покупку оборудования этот план не предполагает. Если нужный эксперимент не помещается в локальные ограничения, сначала уменьшаем его масштаб и оцениваем, какой вопрос всё ещё можно честно проверить.

## Следующий небольшой шаг в notebook

Сформировать и посмотреть **один реальный пример EPIC**: ДНК, one-hot, целевой профиль двух цепей и маску. После согласования этого контракта определить минимальную CNN и loss, затем выполнить короткую ресурсную проверку.

Заполняем notebook по одному небольшому шагу. Ни одна гипотеза этой заметки пока не подтверждена CNN-экспериментом.
